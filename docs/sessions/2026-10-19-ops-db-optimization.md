# 세션 리포트 — 운영·DB 전수 점검과 최적화 (2026-10-19, 49차)

> 요청:
> - 운영과 DB 전체를 파악해 최적화가 필요한 곳을 찾고, 교차 검증·테스트해 목록을 만든다.
> - 목록의 높음~중간을 실행하고, 여유가 있으면 낮음도 한다(Workers 유료 플랜).
> - 남은 일(문서, SESSIONS 네임스페이스 정리)을 마치고 채팅 WebSocket을 기본으로 켜서 배포한다.

## 점검 방법
- **운영 D1(읽기 전용)**
  - 인덱스 정의와 테이블별 행 수를 읽었다. 개인정보는 집계만 봤다(이메일 개별 조회는 정책상 하지 않음).
  - 주요 쿼리 `EXPLAIN QUERY PLAN`과 마이그레이션 적용 기록을 확인했다.
- **Cloudflare 분석(GraphQL)**: 계정 KV 연산(일별·네임스페이스별)과 Worker 요청·오류·CPU p99(14일)를 봤다.
- **응답 시간**: QA 계정으로 GET 엔드포인트 10개를 운영과 스테이징에서 각각 5회 측정했다.
- **실험(스테이징만)**: 같은 키 동시 쓰기, 로그인 rate limit 동시·순차 요청, PBKDF2 반복 상한(로컬 workerd 임시 Worker)을 실험했다.
- **문서 근거**: Cloudflare KV 문서(한도, 일관성)와 Workers Rate Limiting 바인딩 문서를 Context7로 확인했다.

## 발견
| 우선순위 | 발견 | 근거 |
|---|---|---|
| 높음 | **rate limit이 한 번도 걸리지 않았다.** 로그인 무차별 대입, 회원가입, 외부 검색 할당량 보호가 모두 무효였다 | 스테이징에서 분당 5회 한도인 로그인에 동시 20회 + 순차 8회를 보냈는데 전부 401, 429는 0건. KV는 "키 없음" 조회 결과도 60초간 캐시하므로 get이 계속 0을 읽는다 |
| 높음 | KV 쓰기 실패가 로그인·refresh 500으로 이어지는 구조 | rate limit과 refresh 토큰의 `put`에 예외 처리가 없었다. 유료 플랜이라 하루 한도 소진 위험은 낮지만, 같은 키 1초 1회 제한(429)과 장애 시 경로가 남아 있었다 |
| 중간 | AI 하루 한도·예산·생성 잠금도 같은 KV get→put | 몰린 요청이 한도·잠금을 통과한다. Gemini 무료 등급은 모델별 하루 20회 |
| 중간 | 만료된 푸시 구독이 쌓였다 | "404/410이면 호출자가 정리"라는 주석만 있고, 지우는 코드는 없었다. 운영에서 사용자 1명에게 구독 8개 |
| 중간 | 채팅 polling | 처음에는 "WS와 3초 polling이 겹친다"고 보고했다. 실제로는 WS가 `chat_ws=1`인 사용자에게만 켜져 있었다(아래 '바로잡은 판단' 참고) |
| 낮음 | 중복 인덱스 10개, 정렬 임시 B-tree 2곳 | 운영 인덱스 정의와 EXPLAIN으로 확인 |
| 낮음 | 죽은 코드 | 레거시 SHA-256 해시(운영·스테이징 0건), SESSIONS 폴백(2026-04-08 이관 + TTL 30일) |
| 낮음 | PBKDF2 반복 10,000회 | 무료 플랜 CPU 한도에 맞춘 값이었다 |

**문제없음으로 확인한 항목**
- 응답 시간 대부분이 네트워크 왕복이었다(0.22~0.5초).
- 최근 14일 Worker 오류 0건.
- 통계 쿼리 8개는 `db.batch` 한 번으로 묶여 있었다.
- 표지 이미지는 R2 캐시를 쓰고, 책 95권 모두 프록시를 거친다.
- 첫 화면에서 차트와 스캐너 묶음을 받지 않는다.
- 서비스워커 precache 2.1MB는 ADR-001에 따라 일부러 정한 구성이다.

**하지 않은 것과 이유**
- vitals rate limit은 1번 수정 이후 D1에 쓴다. 20% 샘플 비콘이라 양이 미미해서, rate limit 방식을 하나 더 들이지 않았다.
- PBKDF2를 100,000회 넘게 올리지 않았다. 로컬 workerd에서는 600,000회도 32ms였지만, Workers 런타임은 과거 100,000회 상한이 있었다. 운영에서 확인하지 않고 넘기면 가입과 로그인 전체가 실패할 수 있다. 올리려면 스테이징 e2e를 먼저 돌린다.

## 바로잡은 판단
- **"WS와 3초 polling이 겹친다"(점검 보고):** WS는 `localStorage.chat_ws=1`인 사용자만 켜져 있었고, 대부분의 사용자는 polling만 썼다.
- **dcc0c02의 회귀:** WS를 기본으로 켜려고 확인하다가, 채팅 전송이 처음부터 HTTP POST이고 서버가 이를 DO로 넘기지 않는다는 것을 발견했다. 즉 WS는 접속 상태만 실시간이었다. 그래서 dcc0c02(연결 중 polling 30초)는 플래그 사용자에게 최대 30초 지연을 만들었고, 이 상태로 운영에 한 번 배포됐다. 39d64c1에서 해소했다.
- **"같은 키 동시 쓰기 → 429 → 500" 가설:** 스테이징에서 재현되지 않아 기각했다. 동시 15건이 모두 200이었다.

## 검증
- 각 커밋 전에 type-check, lint, build를 통과했다. vitest는 563개에서 602개로 늘었다.
- 핵심 테스트(AI 요약 환불, refresh 내결함성, rate limit)는 수정을 빼면 실패하는 것까지 확인했다.
- 로컬 e2e: TEST 62(AI 태그)만 실패. 로컬에 AI 바인딩이 없어서 나는 것으로 `docs/CI_CD.md`에 정상으로 적혀 있다.
- 스테이징(1차, 3edc18f): 전체 e2e 통과(AI 포함). 로그인 실험을 재현하니 동시 20건 중 5건만 401, 나머지와 순차 8건은 모두 429였다.
- 운영(3edc18f 배포 후)
  - 0020·0021 적용, 중복 인덱스 0개 남음, DB 770KB → 741KB.
  - readonly e2e 통과.
  - 로그인 rate limit 실동작 확인(`401×4 → 429`).
  - GET 응답 시간은 배포 전과 같았다.
- 스테이징(2차, e807527): 전체 e2e 통과. TEST 82(WebSocket 실시간 수신)는 1.9초였다.
- 운영(2차, e807527 배포 후)
  - health와 readonly e2e 통과.
  - QA 계정 임시 모임으로 실제 WebSocket을 확인했다. 연결은 0.72초, HTTP 전송 이벤트는 1.64초에 도착했다. 삭제 이벤트는 그 0.14초 뒤에 왔다. 임시 모임은 삭제했다.
